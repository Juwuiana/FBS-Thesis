# Deploying to Render

The app runs as one Render web service (gunicorn, 1 worker, 4 threads) with a persistent disk
holding the SQLite database and uploaded profile photos. SQLite means **one instance only**: do not
scale horizontally or raise the worker count.

## 1. Before you deploy

- Persistent disks need a paid instance type (`starter` in `render.yaml`).
- The `SECRET_KEY` that used to be in `.env.example` is in git history. If you ever used it for
  anything real, treat it as compromised (Render generates a fresh one for you).
- Demo accounts are **off** in production (`FBS_SEED_DEMO` unset). They all share the public password
  `Password123!`, so never enable that flag on a public site.
- The trained model is not in the repo (`*.joblib` / `*.pkl` are gitignored). Without one the app
  runs a clearly flagged stub. See "Model file" below.

## 2. Create the service

1. Push the `deploy/render` branch to GitHub.
2. Render dashboard → **New → Blueprint** → pick the repo and branch. Render reads `render.yaml`.
3. When prompted, fill in the two `sync: false` variables: `FBS_ADMIN_EMAIL` and
   `FBS_ADMIN_PASSWORD` (at least 12 characters).
4. Deploy. Health check is `GET /health`.
5. Open the service URL and log in with the bootstrap admin. The admin is created on startup only
   while the `users` table is empty, so it is safe to leave set, but **remove both variables after
   the first login** and change the password under Privacy & Security.
6. Edit the admin's details (name, birthday, sex, phone) in the staff screen: the bootstrap fills
   placeholders for those.

`PYTHON_VERSION` in `render.yaml` is `3.13.5`; the test suite was verified in a clean venv on
Python 3.14 with `requirements-deploy.txt`. Change the value if Render rejects it.

## 3. Environment variables

| Variable | Required | Notes |
|---|---|---|
| `FBS_ENV` | yes | `production`. Refuses to start without a real `SECRET_KEY`; enables secure cookies and proxy headers. |
| `SECRET_KEY` | yes | Generated by Render (`generateValue: true`). Changing it signs everyone out. |
| `DATABASE_PATH` | yes | `/var/data/fbs_thesis.sqlite3` (on the disk). |
| `FBS_UPLOAD_DIR` | yes | `/var/data/uploads`. Profile photos go to `<dir>/avatars` and are served only to signed-in users. |
| `FBS_ADMIN_EMAIL`, `FBS_ADMIN_PASSWORD` | first deploy | Creates one approved Health Officer if the users table is empty. Min 12 characters. Never logged. |
| `FBS_ADMIN_FIRST_NAME`, `FBS_ADMIN_LAST_NAME`, `FBS_ADMIN_BARANGAY` | no | Defaults: System / Administrator / Aplaya. |
| `FBS_SEED_DEMO` | no | `1` creates the 3 demo accounts. Local demos only. |
| `FBS_MODEL_PATH` | no | Path to the model file, e.g. `/var/data/model.joblib`. |
| `FBS_SINGLE_SESSION_POLICY` | no | `block` (default) or `replace`. |
| `REQUIRE_ADMIN_APPROVAL` | no | Default `True`: sign-ups need admin approval. |
| `FBS_DEMO_MODE`, `FBS_DEV_NO_AUTH` | no | Leave unset. |
| `PYTHON_VERSION` | yes | Set in `render.yaml`. |

Everything else (`FBS_PROBE_*`, `FBS_*_W`, ...) is optional tuning; see `.env.example`. The
connectivity monitor probes public DNS by default, which is fine on Render.

## 4. Restoring / importing existing patient data

The schema is created and migrated automatically on startup, so for a brand-new deploy you can also
just use the app's CSV import (Admin → Data Management). To carry over an existing database file:

1. On your machine, make a consistent copy (do not copy a live file mid-write):
   ```
   sqlite3 instance/fbs_thesis.sqlite3 ".backup 'fbs_export.sqlite3'"
   ```
   (or stop the local app and copy the file).
2. Enable SSH on the service (Render dashboard → service → **Connect**) and copy it to the disk
   while the service is running; or suspend traffic first so nothing writes concurrently:
   ```
   scp -s fbs_export.sqlite3 SERVICE@ssh.REGION.render.com:/var/data/fbs_thesis.sqlite3.new
   ```
3. In the Render shell, swap it in and restart:
   ```
   cd /var/data
   mv fbs_thesis.sqlite3 fbs_thesis.sqlite3.bak 2>/dev/null
   mv fbs_thesis.sqlite3.new fbs_thesis.sqlite3
   ```
   Then **Manual Deploy → Restart**. Pending migrations run on startup.
4. Imported accounts carry their own users and password hashes, so the bootstrap admin is skipped
   (it only runs on an empty users table). Make sure the imported data contains at least one
   approved Health Officer you can log in with.
5. Existing profile photos: copy them into `/var/data/uploads/avatars/` (previously
   `app/static/uploads/avatars/`), keeping the `user_<id>.<ext>` names.

Backups: the disk is not a backup. Take Render disk snapshots and/or periodically run the
`.backup` command above and download the result. This is patient data: keep copies encrypted and
off public storage.

## 5. Model file

`*.joblib` / `*.pkl` are gitignored so a model is never committed by accident. Options:

- **Recommended:** upload it to `/var/data/model.joblib` (same `scp` method) and set
  `FBS_MODEL_PATH=/var/data/model.joblib`.
- Or commit it deliberately (`git add -f`) after deciding the model and its training data may be
  public.

`requirements-deploy.txt` has no ML libraries. If your model needs them (for example `joblib`,
`numpy`, `scikit-learn`, and the same versions used for training), add them before deploying a
model, or the app will fail to load it.

## 6. Notes

- Logs: Render dashboard → Logs. Passwords are never logged.
- Local development is unchanged: use `requirements.txt` and `.env`. Demo accounts now need
  `FBS_SEED_DEMO=1` in `.env`, or `flask create-admin`.
- Security headers set on every response: `X-Content-Type-Options`, `X-Frame-Options`,
  `Referrer-Policy`. HTTPS is terminated by Render; the proxy headers are trusted via `ProxyFix`.
